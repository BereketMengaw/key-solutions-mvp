# Key Solutions — Restaurant ERP MVP demo

Every agent reads this file first. It is the team's shared rulebook.

## What we are building

A demo of a restaurant ERP for restaurants and cafés in Addis Ababa. It is shown to a
client in about two minutes, so it must be simple, clear and good-looking. Not production.

Four parts:

1. **Waiter** (mobile app, phone) — logs in, picks a table, adds items, sends the order.
2. **Cook** (same mobile app, tablet) — sees orders live, marks them Preparing → Ready.
3. **Backend** (Supabase) — stores everything, deducts stock when an order is sent.
4. **Owner / manager** (website) — sees sales, live orders and stock; adds stock when a delivery arrives.

## The demo story (everything we build serves this)

1. Waiter logs in, picks Table 4, adds 2 Tibs + 1 Macchiato, taps Send.
2. The order appears on the cook's tablet within ~1 second. Cook taps Preparing, then Ready.
3. The waiter's phone shows the order is ready.
4. Ingredients are deducted from stock automatically.
5. Owner's website shows today's sales, live orders, stock levels and a low-stock alert.
6. Owner adds "+10 kg beef" and the alert clears.

If a feature does not help this story, it is out of scope.

## Out of scope for the demo

Real payments (Telebirr / CBE Birr are a "mark paid" button only), receipt printing,
multiple branches, offline mode, hotel rooms, CRM/loyalty, push notifications.

**An agent only edits files in the folders it owns.** If it needs something from another
folder, it says so in its report and the PM routes it. `code-quality` edits nothing.

## Stack

- **Backend:** Supabase (Postgres, Auth, Realtime, RLS). Free tier only.
- **Mobile:** Expo (React Native) + TypeScript, Expo Router, `@supabase/supabase-js`. Ships as an Android APK via EAS free tier.
- **Web:** Next.js (App Router) + TypeScript + Tailwind CSS, `@supabase/ssr`. Hosted on Netlify or Cloudflare Pages — never a `*.vercel.app` link.
- **Package manager:** npm. Each app has its own `package.json`; no monorepo tooling.
- TypeScript `strict` everywhere. No `any` unless commented why.

Internet in Addis is slow: keep dependencies few. Do not add a library for something a few lines of code can do.

## The contract between agents

- `shared/database.types.ts` is generated by `backend` (`supabase gen types typescript`). Mobile and web import types from it and never hand-write table shapes.
- `shared/constants.ts` holds order statuses and roles. Everyone uses these, never string literals.
- `design/tokens.ts` holds colors, spacing, radius, font sizes. Mobile and web use these, never raw hex values.

## Roles

`waiter`, `cook`, `manager`, `owner`. A user's role lives in `profiles.role`.
Login decides the screen: waiter → order screens, cook → kitchen screen, manager/owner → website.

## Order statuses

`sent` → `preparing` → `ready` → `served` → `paid`

## Demo data

Seed data uses a believable Addis café: Ethiopian dishes and drinks (Tibs, Shiro, Kitfo,
Firfir, Macchiato, Buna, juice), prices in ETB, 8 tables, one user per role.
Names and copy must look real but never claim real customers or real integrations.

## Language

English first. Amharic switch arrives in the polish slice; until then put every UI string
in one place per app so translation is a drop-in. Amharic must read native, not translated.

## Definition of done (every slice)

1. The slice's "Done when" test in `docs/slices/` passes, run for real.
2. `npm run typecheck` and `npm run lint` pass in every app touched.
3. `code-quality` has reviewed the change and has no blocking findings.
4. The PM has shown the result to Bereket and he has accepted it.

## Git

- One branch per slice: `slice/NN-name`. The PM merges to `main`.
- Commit messages: short, imperative, plain English.
- **No AI attribution of any kind** in commits or PRs — no `Co-Authored-By`, no "Generated with" lines.
- Never commit secrets. `.env*` files are gitignored; `.env.example` lists the keys.
